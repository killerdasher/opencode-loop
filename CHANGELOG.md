# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- **Controlled self-evolution** (`scripts/evolution.mjs`; docs `docs/evolution.md`): a controlled improvement system for LOOP itself - discovering weaknesses in LOOP's methodology and generating testable improvement proposals through a ten-step evidence-driven workflow. It collects sanitized evaluation outcomes (validated continuity archives + evaluator manifests) into an append-only ledger (re-collecting skips, history is never rewritten; integrity-suspect sources are refused), classifies recorded weaknesses into instructions / references / validation / recovery through a versioned keyword classifier, generates proposals that are **refused unless mapped to recorded failed evaluation cases**, verifies each candidate inside detached git worktrees under the OS temp dir (the active repository and active skill are never touched; `.opencode` data dirs are refused outright), runs the full regression suite on both sides with no shell (`spawnSync`) - by default `scripts/validate.mjs --all` and `tests/harness/selftest.mjs` - and compares every `Summary` tier deterministically: any regression (lower tier pass count, higher failures, missing tier, nonzero exit) hard-rejects the candidate (verdict `REJECTED`, proposal permanently unapprovable, evidence preserved); adoption requires a measurable improvement (strictly more passing checks, zero regressions) **and** an explicit named approver (`--approved-by`), recorded as a decision only - `appliedByTool` is always `false`, nothing is published automatically, and applying a candidate is a manual, human-reviewable step. Model-generated claims are never evidence: the optional `claim` field is carried but labeled `evidence: false`, and verdicts rest on deterministic suite counts only (disclosed proxy limitation: tier counts are structural - renames/splits read as regressions; the bias is conservative). All records are schema-pinned v1 with content-hash ids, secret-shape scanning, and atomic writes. Honest scope: LOOP does not learn model weights and holds no permanent autonomous intelligence - evolution here means improving instruction/reference/validation/recovery *artifacts* through human-approved, regression-gated changes; one candidate/commit-pair per comparison, not a statistical model of LOOP quality.

- **Model capability evaluation** (`scripts/model-eval.mjs`; docs `docs/model-eval.md`; pinned task set `tests/model-eval/taskset.v1.json`): evidence-backed evaluation of LOOP-compatible AI models on identical tasks in controlled environments. Eight capability dimensions (instruction-adherence, tool-calling, coding-correctness, context-management, verification-accuracy, security-reasoning, recovery-behavior, completion-evaluator-adherence) are measured from completed evaluation records that store provider, model identifier, test date, environment, per-task `PASS|FAIL|PARTIAL` results, and re-inspectable evidence paths - never from marketing descriptions (unknown/promotional record fields are refused; records are allowlist-strict). The task set is version-pinned (`v1.0.0`) with a SHA-256-derived `taskSetHash` written into every record, so comparisons between records that did not execute identical tasks are refused rather than silently compared, and differing environments are flagged as directional, never controlled. No ranking is derivable by construction: comparisons emit per-dimension observed counts with an explicit non-ranking disclaimer, and profiles emit counts plus a sample-size classification only (dimensions below `MIN_TASKS_PER_DIMENSION` = 3 tasks are `INSUFFICIENT_SAMPLE`, never scored); completing a record requires an explicit `limitations` statement, carried into every derived profile and comparison. Fail-closed record handling (unknown-field refusal, secret-shape scanner on every write, atomic tmp+fsync+rename writes), deterministic runIds with duplicate refusal, zero external dependencies. No credentials are ever handled or stored (runs are operator-gated with operator-supplied credentials), no provider is called or switched automatically, and the core project tests exercise the framework offline on fixture records with no paid API. **Token-gated limit:** no real model capability profiles ship in this release - zero profiles exist in the repository, and none are inferred from vendor claims; producing one requires an operator-initiated evaluation run.

- **Task profiles** (`scripts/profiles.mjs`; docs `docs/profiles.md`; modular references `references/profiles/{build,debug,refactor,audit,migrate}.md`): adaptive engineering methodologies for the nine-stage loop. Five profiles - BUILD (new functionality), DEBUG (root-cause investigation), REFACTOR (behavior-preserving structure), AUDIT (read-only independent assessment; fixes require explicit operator authorization), MIGRATE (controlled technology/data transitions with rehearsed rollback) - each defining the same seven dimensions: required inputs, relevant analysis stages, verification methods, risk priorities, completion criteria, forbidden shortcuts, and expected evidence. Profiles are selected from explicit user intent only (`--profile <name>` on `/loop`, resolved deterministically by the zero-dependency resolver - unknown names are refused with the valid list, never silently defaulted, and the run continues as the generic loop) and never override the task scope: only the `--profile` flag is stripped, everything else in the task text passes through verbatim. Universal safeguards bind every profile (anchored in each reference and pinned by the validator): the nine stages and the hard safety rules apply unchanged; a profile only adds specificity, never removes a stage or loosens Stage 8 evidence requirements. Resolver behavior is covered by real-module and CLI checks, and every reference file is validator-pinned for all seven dimensions plus the safeguard anchor.

- **LOOP Evaluator** (`scripts/evaluator.mjs`; docs `docs/evaluator.md`): deterministic, evidence-based completion evaluation. A run records what it actually executed into `<project>/.loop/verification.json` — criteria (MUST/SHOULD/COULD with optional deliverable artifact paths), evidence verdicts with optional re-executable argv commands, severity-classified findings, and blockers — and the evaluator derives one of `PASS | FAIL | BLOCKED | NEEDS_REVIEW` from that manifest (exit codes 0/1/2/3). A model-written completion statement carries zero weight: advisory-only evidence caps at `NEEDS_REVIEW`, missing verification derives `BLOCKED` (never a silent PASS), and `--fresh` re-executes every deterministic PASS command, letting the real exit code override recorded claims. Zero external dependencies; reuses the continuity helper's atomic write, secret scanner (both fail-closed), and state inspection; binds to the live continuity run's `taskId` and refuses cross-run/planted manifests. Integrated via a Stage 8 touchpoint in the skill and a completion-evidence section in the continuity reference — the nine-stage methodology is unchanged.

- **LOOP Continuity** (ADR 0002, `docs/adr/0002-loop-continuity.md`; user guide `docs/continuity.md`): durable run state for the nine-stage workflow. A run's state (`ACTIVE | PAUSED | RECOVERY_REQUIRED | BLOCKED | COMPLETED | CANCELLED`, with file integrity tracked separately as `VALID | SUSPECTED_STALE | CORRUPT`) is validated and persisted by an optional, zero-external-dependency helper (`scripts/continuity.mjs`, Node >= 16.7) into `<project>/.loop/continuity.json` - atomic writes (temp + fsync + rename, recoverable temps, and a `repair` path that only removes provably superseded leftovers), sanitized remote-URL identity fingerprints, cancel/complete archiving to `.loop/archive/` with terminal evidence retained (never silently deleted), and a best-effort secret-shape scanner that refuses to persist matches (limits documented in the file header). Four thin commands orchestrate the lifecycle: `/loop-status` (read-only state + git cross-check), `/loop-pause` (stage-boundary pause with recorded next step), `/loop-resume` (gates: integrity, identity, no automatic resumption of an interrupted ACTIVE run, read-only reconciliation first, explicit operator approval, then restore into the nine-stage loop at the recorded stage), and `/loop-cancel` (cancel + archive; reasons retained). Cross-session and cross-model recovery works because the checkpoint is plain files, not session memory; provider-quota or context-limit death is recovered through the same manual resume path. Installers install the helper (`<config>/scripts/continuity.mjs`) and remove it on uninstall. Documented limits: checkpoint writing is prompt-level discipline measured by the behavioral harness (never guaranteed), interrupted stages are not promised bounded loss, one live run per project is an operational rule (generation detects stale snapshots; not a lock), and `--force` does not exist in this release.

- **Continuity reference** (`.opencode/skills/loop-engine/references/continuity.md`): agent-facing protocol - helper search order with the `BLOCKED` degradation contract, state vocabulary, write-before-act timing, resume-gate order, and archive rule.

### Added

- **Requirements traceability in the evaluator** (`scripts/evaluator.mjs`; P12 master-directive Phase 2): criteria may now carry a provenance `origin` (`user` = explicit in the operator's task text, or `implied` / `platform` / `security` / `nonfunctional` for derived essentials) plus an optional `sourceText` verbatim quote. The `outcome` result carries a `traceability` summary that distinguishes **identified** (criteria declared, by origin) from **implemented** (any real coverage), **verified** (freshly re-executed exit 0 in this invocation), and **sufficient** (the derived outcome) - declared is no longer conflated with done. A protective rule closes the omitted-requirement gap: a manifest that declares origins but never traces one to the user's task text caps at `NEEDS_REVIEW` (`criteria-not-traced-to-task`) *even when every recorded command re-executes green* - invented criteria cannot silently replace the operator's objective. Manifests without origin fields stay neutral (backward compatible); the evaluator still cannot detect a requirement that was never recorded (disclosed honestly). Regression tests: traceability summary counts, verified-by-fresh, untraced cap surviving a fully green `--fresh` run, origin/sourceText allowlist refusals, legacy neutrality. Validator pins the guard with a content check and a defect-injection mutation. Docs updated in `docs/evaluator.md` (schema, outcome table, traceability section, capability boundary). A/B pilot preparation was audited and found already complete in `tests/comparison.md` (solo-maintainer batch plan 4+4 runs, model pinning, adjudication and authorization gates) - no duplicated work.

### Added

- **Fresh-Context Review, an optional independent-verification capability** (`.opencode/skills/loop-engine/references/fresh-review.md`; P12 master-directive Phase 3): in-session adversarial review shares the implementer's context, and its strongest known weakness is anchoring - the same context that built the plan reviews it. The new reference defines an optional deep-mode/high-risk review performed by a **separate OpenCode session** (any model): the implementer assembles an evidence package (original objective verbatim, requirements and acceptance criteria, the actual git diff, test evidence with real exit statuses, disclosed limitations, and the implementer's report **last, labeled as claims**); the reviewer works read-only, re-derives from evidence instead of adopting the narrative, re-runs recorded verification commands where runnable, traces every MUST criterion against the objective text, and reports findings that are reconcilable by construction (`CONFIRMED | REFUTED | UNCONFIRMED`, each against actually-executed evidence). The implementer then reconciles every finding in the original session: CONFIRMED findings enter the evaluator manifest and gate PASS by the normal severity rules; REFUTED/UNCONFIRMED findings are answered with evidence, never silently dropped; the review document lives in uncommitted `.loop/reviews/`. Honest limits stated in the reference itself: no runtime enforces the protocol (agent-followed procedure), a different model does not automatically make a review independent or correct, one review is one more sample - not statistical evidence, and a declined review (no budget for another session) is a legitimate recorded outcome. SKILL.md wires the offer into Stage 6 (deep mode, trust-chain work, or accepted MEDIUM+ findings); never mandatory, never auto-run. Validator pins the reference with a content check plus a deletion mutation.

- **Continuity recovery check: cross-model resume** (`tests/harness/selftest.mjs`; recovery scenario 7): a state written by a different session (different `sessionId`/`model` in `createdBy`) must not block pause→resume or trip the identity gates - the checkpoint is model-agnostic by design, now pinned by a real-module test. Already-covered scenarios verified, not duplicated: moved/cloned project (identity mismatch refusal), stale generation snapshots and temps, corrupt-state refusal-not-wipe, quota-death pause/resume with generation bumps.

### Fixed

- **Evaluator: `record` now refuses a manifest bound to another run** (found in P11 closeout, fixed in the P12 master-directive Phase 1): binding to the live task happened only when the manifest had no binding yet, so a manifest left over from a completed or different run silently absorbed the new run's records and reported `ok:true` - the mis-binding surfaced only later, when `outcome` refused the whole derivation with `cross-run-evidence`. `record` now checks the live continuity state before merging: when an identity-matching live task exists and the manifest is bound to a different task id, the record is refused up front with both task ids and the explicit remedy (back up and remove `.loop/verification.json`, then record fresh evidence) - nothing is written, the stale manifest is preserved untouched, same-task re-records stay allowed, and standalone usage without a live run is unchanged (binding there stays guarded by `outcome`). Regression tests (free self-test): refusal with both task ids named, manifest preserved byte-wise, explicit-reset path binds cleanly to the new task, same-task update allowed, no-live-run record allowed. Validator pins the refusal with a content check and a defect-injection mutation. Documentation updated in `docs/evaluator.md`.

- **Documentation drift reconciled with the shipped project** (pre-final recon findings): the README "Repository structure" tree, the Commands/Configuration section, and the Documentation table pre-dated the P5–P7 features — `--profile` and the four deterministic helpers (`evaluator.mjs`, `profiles.mjs`, `model-eval.mjs`, `evolution.mjs`) plus their docs were absent, and the automated-check count was stale ("more than 280"; actual 411 validator + self-test checks). `docs/architecture.md` — cited by the README as the full component design — did not mention the evaluator, profiles, model-eval, or evolution at all; it now covers the two profile/continuity references in the components diagram, explicit-flag-only profile resolution in the data flow, four new design-decision entries, a deterministic-helpers section (evidence location + fail-closed rule per helper), and the helper Node 16.7+ compatibility line. Documentation-only change; no behavior, code, or test changes.

- **Evaluator: a recorded PASS can no longer derive PASS.** P9 remediation of the confirmed read-only-audit finding (2026-11-09): in default mode the evaluator treated a *recorded* `PASS` verdict that carried a re-executable command as fully deterministic coverage, so a fabricated or stale claim ("the suite passed" with a command that actually exits 1) derived a green `PASS` without running anything — the real exit code was checked only under `--fresh`, which the skill described as optional ("use it in the final verification pass"). A recorded command claim is now a claim, not proof: exec-backed evidence that was not re-executed in the same invocation caps the outcome at `NEEDS_REVIEW` (new coverage state `RECORDED_NOT_REEXECUTED`, reason code `deterministic-evidence-not-re-executed`), and `PASS` is only derivable from a `--fresh` invocation whose re-executions exited 0 (`docs/evaluator.md` outcome table corrected accordingly; the skill reference now makes `--fresh` mandatory in the final verification pass). Regression tests: default-mode caps on a recorded PASS whose command really fails (blind `NEEDS_REVIEW`, `--fresh` exposes `FAIL` exit 7), explicit missing-execution-evidence case, unstartable fresh re-execution derives `BLOCKED`, and the recorded-claim path can never reach PASS like the advisory-only path already could not.

- **Installers refuse redirected destinations (symlinks, junctions, reparse points).** P9 remediation of the confirmed finding: both installers dereferenced every destination path component and wrote through links — a junctioned `destRoot` (or a junctioned `skills` subdirectory) silently redirected all installed files *outside* the intended destination while the installer reported success at the canonical path (reproduced on both `install.ps1` and `install.sh`). Both installers now run a containment preflight before any mutation (install and uninstall): every component between the operator-provided root and each destination must be a real directory, otherwise the run is refused with the resolved real target and a remediation hint. Legitimate deliberate redirections are still possible via an explicit opt-in (`--allow-redirected-destination` / `-AllowRedirectedDestination`), which prints the resolved target instead of breaking silently. Regression tests (PowerShell + bash, temp dirs): link-at-destRoot refused with zero writes, opt-in proceeds and lands at the resolved target; the validator pins the preflight, the opt-in flag, and the reparse/symlink detection (with defect-injection mutations).

- **Ownership-aware uninstall preserves customized/user-owned files.** P9 remediation of the confirmed finding: uninstall moved any existing loop command/skill/helper out of the destination regardless of content — a user's own (or user-modified) `/loop` file was relocated to the backup tree on a command they expected only to *remove LOOP*, even where LOOP had never installed anything. Both uninstallers now only remove paths byte-identical to LOOP's current sources; any differing path makes the whole uninstall refuse atomically (nothing is removed, all targets preserved, conflicts listed with the manual-removal / opt-in remedy). The explicit override (`--force-customized` / `-ForceCustomized`) removes the conflicting paths too, backing them up first. Regression tests (PowerShell + bash): user-owned-file-only destination refused with the file intact and no backup side effects; LOOP-install-then-user-modify refused atomically (all three targets kept); forced uninstall removes all with the modified content preserved in the backup; pristine installs uninstall unchanged as before; the validator pins the ownership flag (with defect-injection mutations).

- **Identity mismatch enforcement gap** (found by the new real-module tests, fixed before any command shipped): the helper detected a project identity mismatch but only *enforced* it when the caller supplied an expected root; a direct state-mutating call without that argument could operate on another project's checkpoint. Mutating operations now derive the authority from the project root they were invoked on.

### Changed

- SKILL.md: Stage 0 refuses a silent second run while a live checkpoint exists and, with the helper available, writes stage-entry checkpoints (write-before-act); Stage 8 records completion through the helper and lets early stops stay PAUSED for later `/loop-resume`. Behavior without the helper is unchanged (continuity operations report `BLOCKED`).
- Validation grew with the features: structural checks for the four continuity commands (frontmatter, description, `$ARGUMENTS`, reference route, `BLOCKED` path, and the absence of any override flag), helper content checks (zero-dep, no-network, status vocabulary, documented scan limits), installer matrix assertions for helper install/uninstall byte-identity, and nine new defect-injection mutations. The behavioral self-test grew from 79 to 113 checks, importing the actual helper module (no mirrored test-only model).

## [0.3.1] - 2026-11-05

Reliability, safety, and engineering-quality hardening of the behavioral runner.

### Security

- **Behavioral runner safety contract** (`tests/harness/run-case.mjs`, new `tests/harness/safety.mjs`): an unattended evaluation no longer enables unrestricted automatic permission approval silently. A model run is now refused (exit 4, before any side effect) unless the operator acknowledges it explicitly with new `--allow-auto`; `--build-only` stays free of any acknowledgement. With acknowledgement, the runner (a) writes a least-privilege permission config to the evidence dir and delivers it through the documented `OPENCODE_CONFIG` tier — hard-denying external-directory access, `webfetch`, `websearch`, `*.env` reads, and `curl`/`wget` bash commands (explicit `deny` rules are the one thing OpenCode's auto mode does not approve) — and (b) builds the child environment from an allowlist (`keeperEnv`) so credential-shaped variables (API keys, `*_TOKEN`, SSH agents) are never inherited by the evaluated session — matched case-insensitively on Windows, whose real spellings are `Path`/`ComSpec`/`SystemRoot` (caught on a live machine: the original case-sensitive registry silently dropped `ComSpec` and `SystemRoot` from the evaluated session, degrading node/npm/PowerShell instead of merely scrubbing credentials), and case-sensitively on POSIX where `path` is a different variable; operator-named extras can be forwarded via `--env-pass NAME,...` (values never printed; the report records the *count* of dropped variables, never their names). Both A/B arms receive identical permission rules and identical env scrubbing. Documented honestly as containment, not an OS sandbox: bash/edit/read remain allow by default and the user's global OpenCode config still merges in (full isolation taxonomy now in `tests/harness/README.md`; SECURITY.md scope extended to the harness).

### Fixed

- Behavioral runner (unattended mode): the console summary printed the *names* of dropped credential-shaped environment variables while every report records only their count — contradicting the documented contract that names are never printed. Which variables exist on a machine is not public content, and runner console output often gets pasted into bug reports. The runner's console now shows the count-only summary via `scrubSummary()` (`tests/harness/safety.mjs`); operator-forwarded `--env-pass` names are unchanged, because the operator supplied those names. Regression-tested in the free self-test (`safety:scrub-summary-count-only`, `safety:scrub-summary-empty`, `runner:scrub-summary-helper-in-use`).
- Behavioral harness on POSIX: `runFixtureTest` executed the fixture's command string with `shell: false` on non-Windows platforms, so `spawnSync` treated the whole string (`node test/x.test.mjs`) as a single filename — every seeded-state check failed with `ERROR` on ubuntu CI while Windows passed (first CI run to execute the harness self-test on Linux). Commands now run through a shell on every platform, with a pre-flight executable probe (`where` / `command -v`) so a missing executable stays an `ERROR` (broken environment) and can never be misread as a `FAIL` (red suite). Two free self-test checks guard both behaviors.
- Installers (`install.ps1`, `install.sh`): timestamped backups were created **in place** — `commands/loop.md.backup-<ts>` and, for the skill, `skills/loop-engine.backup-<ts>` — but OpenCode discovers every directory containing a `SKILL.md` under `skills/`, so the overlaid backup came back as a phantom skill (the just-replaced version, live again). Observed with a real overwrite install on 2026-11-04. Backups now go to a sibling root (`<dest>-loop-backups\<timestamp>\<tree>`) outside all discovery directories, tree structure preserved; legacy in-place backups from older installers are left untouched. Installer tests assert the new location and that no `*backup*` residue remains inside `commands/` or `skills/`.

## [0.3.0] - 2026-11-03

Independent engineering audit and behavioral validation.

### Added

- **Behavioral evaluation harness** (`tests/harness/`): semi-automated execution of evaluation Cases A–I — isolated fixture repositories (git-identity-isolated, temp-dir only), one model session per run through the officially documented `opencode run --format json` path, evidence collection (transcript, git diff, independent harness re-run of the fixture suite), and objective criteria with a four-level verdict (`PASS` / `FAIL` / `BLOCKED` / `REVIEW`, precedence FAIL > BLOCKED > REVIEW > PASS). Manual checkpoints return `REVIEW` and are adjudicated next to the evidence; the harness never auto-promotes them.
- **Free harness self-test** (`tests/harness/selftest.mjs`, run in CI): proves fixtures build, seeded states are real (failing fixtures fail, green fixtures pass, Case G's blocker blocks), criteria can both pass and fail, and the evidence parsers hold against the pilot-run defects. 66 checks, no model calls.
- **Behavioral evaluation rubric rewrite** (`tests/evaluation.md`): per case — controlled initial conditions, test objective, observable expected/forbidden behavior, evidence, and objective PASS/FAIL/BLOCKED/REVIEW criteria mapped to harness check IDs; honest result ledger (Case A pilot executed; B–I not yet run).
- **A/B comparison methodology** (`tests/comparison.md`): controlled protocol comparing standard OpenCode execution vs LOOP on identical tasks/snapshots/model/permissions, with metric definitions, anti-gaming reporting rules, and an explicit ledger stating **no comparative results exist yet**.
- **ADR 0001** (`docs/adr/0001-runtime-orchestration.md`): compares skill-only, skill+plugin, and external-orchestrator architectures against official OpenCode APIs (verified); retains skill-only and records revisit triggers.
- Validator checks: evaluation-framework alignment (rubric vs in-session guidance must cover the same Cases A–I), changelog currency (a version beyond 0.1.0 must be documented, newest-first), reporting contract (iteration banner, `SETTINGS:` restatement, five-label status vocabulary), `.gitignore` must exclude behavioral evidence, CI must run the harness self-test — each with a mutation proving it can fail.

### Fixed

- Harness pilot defects (found by executing Case A, not by inspection): phantom diff paths from trimming `git status --porcelain` output (`src/range.mjs` parsed as `rc/range.mjs`); the harness's own LOOP install polluting the scope check (arm setup is now committed to the fixture baseline without touching user work); `read`/`skill`/`glob` tool events misclassified as file writes (corrupted ordering facts); running/completed tool-event pairs double-counted.

### Changed

- CI runs the free harness self-test in addition to the three validator modes.
- `walkFiles` in the validator excludes `tests/harness/evidence/` (transient local run output is not repository content and must never fail repository checks).

## [0.2.0] - 2026-11-02

Verified rebuild of LOOP. Same public interface as 0.1.0 (`/loop` command, `loop-engine` skill, file layout, flags), re-engineered and proven against OpenCode v2.2.5 with an end-to-end live-session run.

### Added

- End-to-end verification in a live OpenCode v2.2.5 session: skill load, `$ARGUMENTS` flag parsing (`SETTINGS: mode=... iterations=...`), Stage 0-8 execution, `LOOP | ITERATION n/N` banner, and byte-level artifact confirmation of the produced file.
- `stage:` line in the iteration reporting banner (the 0.1.0 banner carried changed/verified/key findings/next only).
- `--dry-run` / `-DryRun` mode in both installers, with a test scenario proving it changes nothing.
- Backup-clobber regression scenario: a 60-second marker window proves an overwrite never destroys an earlier backup, for both installers.
- Secret-pattern scan in the validator (private-key blocks and GitHub/AWS/Slack/OpenAI-style token shapes).
- Flags-only invocation fallback: `/loop --mode deep` with no task text now uses the conversation objective.
- `.gitattributes` enforcing LF endings for `*.sh`, so a Windows clone cannot break `install.sh`.

### Changed

- Installer test matrix: 16 scenarios (fresh install, idempotent rerun, overwrite refusal, overwrite-with-backup, clobber window, dry-run, project scope, uninstall), executed against temporary directories only for both installers.
- `/loop` command invokes the skill tool in a parameter-agnostic way (0.1.0 hard-coded `id`).
- Validator split into `--self-test` and `--install-test` modes with 11 defect-injection mutations that must each be detected; relative-link verification upgraded from plain existence checks (which hide case mismatches on Windows) to case-exact resolution.
- Documentation rewritten; fixed the broken `<owner-placeholder>` release link from 0.1.0.

## [0.1.0] - 2026-10-30

Initial release. LOOP is an iterative engineering workflow for OpenCode, not a finished workflow engine; treat this release as a carefully tested starting point.

### Added

- `/loop` command (`.opencode/commands/loop.md`) with `$ARGUMENTS` handling, `--max-iterations` (1-10, default 5) and `--mode focused|balanced|deep` flags, graceful invalid-argument handling, and conversation-context support when no task argument is given.
- `loop-engine` skill (`.opencode/skills/loop-engine/SKILL.md`) implementing the eight-stage iterative lifecycle (objective acquisition, reconnaissance, solution-space exploration, planning, implementation, verification, adversarial review, improvement, convergence) with hard safety rules, iteration management, and an evidence-based reporting contract.
- Skill references: quality gates and reporting format, adversarial review methodology, and runtime guidance for nine canonical evaluation cases.
- Windows installer (`scripts/install.ps1`) and POSIX installer (`scripts/install.sh`): global install by default, project-local option, explicit destination override, backup-before-replace, content-verified uninstall.
- Repository validator (`scripts/validate.mjs`) with `--selftest` mode: structural and frontmatter checks, reference and documentation integrity, ASCII-portability enforcement, sandboxed installer tests, and defect injection proving the checks detect breakage.
- Evaluation suite (`tests/evaluation.md`) with nine cases and disqualifiers.
- Documentation: `docs/architecture.md`, `docs/design-principles.md`, README, CONTRIBUTING, SECURITY policy, and this changelog.
- GitHub Actions workflow running the full validator on Ubuntu and Windows.
